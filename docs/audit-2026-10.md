# Audit — October 2026

Pre-build audit for the functional completion pass. Nothing in this document
has been fixed; this is the state as found.

Method: backend endpoints read from `backend/src/api/*.py` and cross-checked
against the live FastAPI `app.routes` object (not inferred from the frontend).
Frontend calls extracted from `frontend/src`. Runtime checks run against
`npm run dev` on localhost and against the live Lightsail backend.

---

## 0. Headline findings

Four things are broken badly enough to call out before the detail:

1. **The deployed frontend cannot call the deployed backend at all.** `CORS_ORIGINS`
   is set to `memoir-project-frontend-deho.vercel.app` with no scheme. Browsers
   send `Origin: https://…`. Starlette compares exactly, so every browser request
   from production fails preflight. Proven against the live service (§5).
2. **Every share link generated in production 404s.** The backend builds links from
   `SHARE_LINK_BASE_URL=https://memoirproject-frontend-eight.vercel.app/share`,
   but the frontend serves the reader at `/contribute/[token]`. The path is wrong
   *and* the host is a different Vercel deployment from the one in `CORS_ORIGINS`.
3. **Real auth tokens are sitting in `localStorage` right now** — `access_token`
   and `sb-cyaqbvoifzawsdfcfysx-auth-token`. Current code does not write them
   (they are leftovers from an earlier build), but logout does not clear them
   either, so they persist indefinitely.
4. **There is no route protection.** `/memories` and `/profile` both return 200
   to an unauthenticated visitor, and `/memories` renders the subject's real
   name from cached `localStorage` without any session check.

## 3. Mismatch table

### 3a. Endpoints the new spec needs that DO NOT EXIST

| Needed for | Endpoint required | Why nothing existing works |
|---|---|---|
| §5a "Autosaves as a draft"; adding media to an open memory | **`PATCH /api/memories/{memory_id}`** (`title?`, `body_text?`, `status?`, `media_asset_ids?`) | There is no memory update route at all — only create, feed, delete. A draft can be created once and never amended. |
| §5a "text saved BEFORE any file upload" | same as above | `POST /api/memories` takes `media_asset_ids` at creation, so text-first forces a second write that has no endpoint. |
| §1/§4 `/memoirs/[id]/*` route scoping | **`GET /api/memoirs/{memoir_id}`** | No single-memoir read. Every screen fetches the whole list and filters client-side, which also means ownership of a specific id is never verified in one call. |
| §5b chat accept → persist | **`POST /api/memoirs/{id}/chat/apply`** (or extend `organize/apply` to accept a chat action) | `POST /chat` returns `ProposedAction[]` with **no id**, and they are not persisted. `organize/apply` takes a stored `proposal_id` from the *organize* pipeline and cannot accept a chat action. |
| §5b chat actions `create_chapter`, `split_chapter` | **`POST /api/memoirs/{id}/chapters`** and a split route | The schema can propose both; no endpoint can apply either. |

**Partially applicable chat actions** — these four can be applied today by
translating the proposal into existing manual endpoints, no new backend needed:
`move_memory` → `PUT …/memories/{id}/move`; `rename_chapter` and
`rewrite_chapter_summary` → `PUT …/chapters/{cid}`; `reorder_chapters` →
`PUT …/chapters/reorder`; `merge_into_chapter` → repeated `move_memory`.

### 3b. Endpoints that exist but the frontend never calls

`POST /api/auth/refresh` (**no refresh anywhere — sessions simply expire**),
`POST /api/transcript/` and `/retry` (§5a requires the retry),
`GET /api/memoirs/{id}/organize/memories`, `/organize/history`,
`GET /api/search/`, `PATCH /api/comments/{id}/hide`, `DELETE /api/comments/{id}`,
`DELETE /api/memories/...`, `GET /api/memoirs/{id}/share-link`,
`GET /api/share/{token}`.

### 3c. Shape disagreements

None found. Zod schemas at the client boundary match the Pydantic response
models for every endpoint actually in use. `reorderChapters` matches
`ChapterReorderRequest` (full ordering, not a delta).

### 3d. Screens needing data no endpoint returns

- **§7 profile "memory count" per memoir** — `GET /api/me/profile` does return
  `memory_count`, so this is fine.
- **§1 draft/published split** — `status` is returned by `/api/me/profile` but
  **not** by `GET /api/memoirs/` (which returns raw memoir rows; `status` is on
  the row, so it is present — usable, but undocumented and unvalidated by any
  Zod schema on the client).
- **§5b contributor line per chapter** ("Sara & James · family memories") — no
  endpoint returns contributor names per chapter. Derivable client-side by
  joining chapter memories to participants, at the cost of an extra call.

### Note on §9b/§9c (not bugs — existing state)

- **All six security headers from §9c already exist** in `src/proxy.ts:69-74`,
  including `Permissions-Policy: microphone=(self)` and a nonce-based CSP.
  They are *not* currently verified on 404/500 responses.
- **`middleware.ts` must not be created.** This Next version renamed the
  convention to `proxy.ts` and warns on `middleware.ts`; the file already exists
  and runs on every request. §9b's logic belongs **inside `src/proxy.ts`**.
- **§9a's premise does not hold.** `@supabase/*` is not a frontend dependency at
  all — auth is already backend-issued httpOnly cookies. There is no browser
  Supabase client to migrate. The real §9a work is (a) clearing the legacy
  localStorage keys and (b) moving the reader token to a cookie.
- `NEXT_PUBLIC_` vars in use: `API_BASE_URL`, `API_TIMEOUT_MS`, `SUPABASE_URL`,
  `SUPABASE_ANON_KEY`. No service-role key, no reader JWT secret, no AI keys.
  The two Supabase vars are declared in `lib/config/env.ts` but nothing imports
  it — they are dead config and should go.

## 5. Does auth work end to end right now?

**Locally: yes. In production: no — nothing does.**

Proven against the live backend:

```
Origin: https://memoir-project-frontend-deho.vercel.app  → HTTP 400
Origin: memoir-project-frontend-deho.vercel.app          → HTTP 200
                                   access-control-allow-origin: memoir-project-frontend-deho.vercel.app
```

The only origin the backend accepts is one no browser can ever send. Login,
signup, feed, everything fails at preflight before any auth logic runs. Both
Vercel hosts return 200, so there are two frontend deployments live and the
config points at a different one for CORS than for share links.

Mechanically the design is sound: httpOnly `access_token`/`refresh_token`
cookies set server-side, owner and reader credentials on separate paths,
`COOKIE_SECURE=true` and `COOKIE_SAMESITE=none` correct for cross-site. The
`COOKIE_SAMESITE` key typo (trailing space) found earlier this session is fixed
in the pipeline's env block. What is missing is any **refresh** call (B12) and
any **route guard** (B4).

## 6. What I could not verify

- **375px / 768px runtime behaviour.** Chrome's `resize_window` does not change
  the rendered viewport in this environment (same limitation hit during the
  design extraction). Responsive behaviour was read from the CSS breakpoints
  instead; no page was visually confirmed at 375px.
- **Console errors on authenticated pages.** `/memories` was clean apart from
  the expected `Failed to fetch` (no local backend). `/chapters`, `/memoir`,
  `/profile`, `/contribute/[token]` were not exercised with a live session.
- **Whether the memoir feed is N+1** (§10). The backend batches transcripts
  deliberately and the feed query looks bounded, but I did not count queries
  against a memoir with many memories.
- **PDF export output** — not triggered; cannot confirm photographs render.
- **Google OAuth** — no backend endpoint and no frontend client exists, so §3a/§3e
  "Continue with Google" has nothing behind it today. Needs a decision: Supabase
  OAuth redirect (frontend dependency + callback route) or a backend-mediated flow.

## 8. Decisions taken (2026-10-12)

1. **Google OAuth: dropped.** Not wanted. `/signin` and onboarding step 5 are
   email + password only. Removes the sessionStorage-survives-OAuth-redirect
   concern from §3e entirely.
2. **Chat apply: existing endpoints only.** No new backend route. "Accept"
   translates a proposal into the real endpoints that already exist —
   `move_memory`, `rename_chapter`, `rewrite_chapter_summary`,
   `reorder_chapters`, and `merge_into_chapter` (repeated moves). Each of those
   re-verifies ownership server-side, so nothing is trusted from the client
   beyond ids the owner could already act on manually. The AI must be
   constrained so it never proposes `create_chapter` or `split_chapter`, which
   have no endpoint and would otherwise produce an un-acceptable proposal.
3. **Canonical host: `https://memoir-project-frontend-deho.vercel.app`.**
   Confirmed serving the current build. `CORS_ORIGINS` gains the missing
   scheme; `SHARE_LINK_BASE_URL` is repointed here, and the reader route is
   renamed `/contribute/[token]` → `/share/[token]` to match §8 and the link
   the backend generates. `memoirproject-frontend-eight` ("Memoir Archive") is
   stale and is not referenced by anything after this change.
